# 사이 — 모바일 우선 UX/UI 재설계 명세

작성일: 2026-09-25. 배포 화면 검토: 2026-09-24~25. 대상: https://a1-3-green.vercel.app/ . 산출물: 제품 재설계 명세 + 같은 폴더의 `UX_UI_PREVIEW.html` 화면 시안. **운영 프런트엔드와 백엔드는 이번 산출물에서 수정하지 않는다.** 본문의 크기·시간·간격은 별도 실측 표시가 없으면 **구현할 설계값**이며 현재 서비스의 측정값이 아니다. 시안의 토론 문장은 실제 배포 화면에서 읽은 핫도그 토론을 사용한다. 시안은 정적 디자인 자료이며 AI 생성이나 API 성공을 흉내 내지 않는다.

## 1. 실제 화면 검토 결과

### 1.1 검토 범위와 증거

Codex 브라우저에서 배포 URL을 직접 사용했다. 390×844, 768×1024, 1440×1000 CSS px로 뷰포트를 설정했다. 화면 캡처와 접근성 트리, 읽기 전용 DOM 측정을 함께 확인했다. 세 폭 모두 동일한 모든 상태를 전수 검수한 것은 아니다.

| 관찰 ID | 직접 수행·확인한 내용 | 범위·한계 |
|---|---|---|
| E01 | 빈 입력에서 분석 클릭 → “토론할 주제를 입력해주세요.” | API 무호출은 브라우저 네트워크 측정 아님. 현재 `app.js`의 early return으로 별도 확인 |
| E02 | 390px 핫도그 입력 → “핫도그는 샌드위치에 속한다.” → “샌드위치 VS 별도 범주” → 시작 | 모바일 입력·Motion·Opening 확인 |

공개 모드가 Mock인지 서버 설정을 직접 확인하지는 않았다. 화면 문장은 로컬 `mock_service.py`와 일치하지만, 이를 모드 확정으로 표현하지 않는다. Mock일 수 있다는 점은 평가 결격 사유가 아니다. 반복 문장은 실시간 모델 품질 평가 근거로 사용하지 않았다. 실제 API 오류·Timeout·Safe failure·최대 글자 수 도달·모바일 가상 키보드·스크린리더 낭독은 **미확인**이다.

## 2. 최종 디자인 방향

**브랜드: 사이. 콘셉트: ‘두 생각 사이, 다음 한마디’.** 한 주제를 사이에 둔 두 관점을 차분한 대화 지면으로 보여준다. 읽기 편한 따뜻한 백색, 짙은 잉크색 본문, 청록 A와 자주 B를 사용한다. 중립 행동 버튼은 잉크색으로 통일한다. 어느 입장도 기본 승자처럼 강조하지 않는다.

사용자는 “주제 하나만 적으면 흥미로운 공방이 시작된다”, “방금 말을 이렇게 받아치는구나”, “판단은 내가 한다”를 느껴야 한다. 브랜드는 호기심 있고 명료하며 약간 재치 있지만, 토론자를 감정을 가진 사람으로 연출하지 않는다. 실제 사람 얼굴·가상 이름·감정 게이지·승률·득점·왕관·네온·타이핑 흉내·자동 재생되는 장식은 쓰지 않는다.

기존 CLASH LAB 이름, 영문 슬로건, Hero, 설명, 메뉴명, 빈 화면, 버튼 문구, 기술 다이어그램, 검정/형광 팔레트, 공통 카드 스타일을 폐기한다. **보존하는 것은 순차 토론·세 메뉴·양측 공통 질문·중립 요약·사용자 선택이라는 기능 계약뿐**이다. 기존 문구를 보존 전제로 삼지 않는다. 사용자가 지정한 “어느 쪽이 더 설득력 있었나요?”와 “아직 모르겠다”는 제품 계약으로 유지한다.

## 3. 완성된 정보 구조

### 3.1 사이트맵

```text
사이
├─ #home  시작하기
│  ├─ 주제 입력 / 분석
│  ├─ 필요한 경우: 상황 질문 → 상황 정리
│  └─ 토론할 문장 확인 → 문장 수정(성공 1회) → 양측 소개
├─ #debate  토론 보기
│  ├─ 첫 입장 → 주고받기
│  ├─ 질문하기 또는 계속 보기 → 함께 답하기(질문 시)
│  ├─ 쟁점 되짚기 → 마지막 한마디
│  └─ 토론 정리 → 내 선택 → 선택 완료
└─ #how-it-works  이용 안내
   ├─ 이용 순서 / 토론자가 다른 이유 / 판단은 사용자에게
   └─ 보관·정보 한계 / 기술 설명(접힘)
```

세 개의 해시 라우트로 구현한다. 현재 라우트 한 개만 `hidden=false`. 페이지 이동은 요청이나 세션을 초기화하지 않는다. Home 복귀 시 진행 중 세션이 있으면 “보던 토론으로 돌아가기”를 먼저 표시하고 새 주제는 별도 동작으로 둔다. 토론 없이 Debate에 직접 진입하면 빈 상태와 “주제 고르러 가기”. 새로고침으로 상태가 없어진 경우 “이 토론은 이어 불러올 수 없어요. 새 주제로 시작해 주세요.”를 표시하되, 최초 직접 방문과 복원 실패를 구분할 근거가 없으면 일반 빈 상태만 쓴다.

| 화면 | 목적·노출 정보 | 주요 행동 / 핵심 CTA | 보조 행동 | 숨길 정보 | 다음 이동 조건 |
|---|---|---|---|---|---|
| Home | 가치 제안, 주제 입력, 예시, 일회성 안내 | 주제 적기 / 토론 준비하기 | 예시 선택, 이용 안내 | 내부 분류·서버 구조 | trim 후 유효 입력 |
| 분석 중 | 제출한 주제, 실제 처리 단계 | 기다리기 / 준비 중 비활성 | 입력은 보존 | 가짜 완료율·예상 시간 | API 성공 분기 |
| 상황 질문 | 원문 접힘, 현재 질문 1개, 답변 수 | 답 선택 후 / 답변 보내기 | 허용 시 잘 모르겠다·직접 입력 | 총 질문 수 추정·ID | 응답 성공 시 다음 질문 |
| 상황 정리 | 직접 본 일/전해 들은 이야기/내 해석/모르는 부분 | 이 내용으로 정리하기 | 주제부터 다시 작성 | 근거 없는 사실 확정 | debate_ready=true 및 사용자 확인 |
| 문장 확인 | Motion, 양측 입장, 사고 방식, 사실 전제(있을 때) | 이 주제로 토론 보기 | 문장 다듬기 1회 | Persona ID·truth_mode 코드 | 준비된 Motion 확인 |
| 문장 수정 | 기존 문장, 1200자 제한, 적용·취소 | 수정한 문장 적용 | 취소 | 서버 오류 원문 | 성공 시 전체 Motion 다시 렌더링 |
| 시작·첫 입장 | 논제, 양측 소개, 첫 발언 | 다음 발언 보기 | 이전 발언 읽기 | 엔진 상태 | 검증된 응답 도착 |
| 주고받기 | 현재 발언, 직전 상대 발언, 진행 단계 | 다음 발언 보기 | 앞선 발언 보기 | 추정한 반박/양보 라벨 | 다음 응답 또는 질문 대기 |
| 질문 선택·입력 | 양측 공통 질문, 선택 사항 안내 | 질문 보내기(입력 시) | 질문 없이 계속 보기 | 한쪽만 질문 옵션 | 전송 성공 또는 생략 성공 |
| 함께 답하기 | 사용자 질문 고정 문구, A 답변 후 B 답변 | 다른 쪽 답변 보기 | 이미 나온 답변 읽기 | 동시 생성처럼 보이는 진행 | 양측 답변 완료 |
| 쟁점 되짚기 | 이전 공방의 전체 원문, 기존 충돌 해결 발언 | 다음 발언 보기 | 앞선 발언 참조 | 자동 생성한 새 논점 요약 | 서버 단계 전환 |
| 마지막 한마디 | 단계 안내, 양측 최종 발언 | 다음 발언 보기 / 토론 정리 보기 | 전체 토론 읽기 | 승리·패배 예고 | completed=true 후 사용자 요약 진입 |

### 3.2 데이터 계약과 구현 경계

확인 파일: `src/web_app/contracts.py`, `src/web_app/api.py`, `src/web_app/mock_service.py`, `src/web_app/live_service.py`, `public/app.js`. 이것은 **현재 로컬 코드 근거**이며 배포와 같은 커밋이라고 확인한 것은 아니다.

| 표현 | 현재 데이터 | 이번 MVP 구현 | 추가 데이터 필요 시 |
|---|---|---|---|
| 논제·입장 | motion, side_labels | 원문 그대로, 안전한 텍스트 렌더링 | 모호한 A/B를 UI가 자동 찬반 번역하지 않음. 서버 입장명 품질 보완 |

| 상황 요약 | context_summary, debate_ready | 네 그룹의 실제 값 표시 | 잘 모르겠다는 답은 확정 사실처럼 이름 바꾸지 않음 |
| 최종 정리 | key_clashes, side_a_strong_points, side_b_strong_points, agreements, unresolved | 다섯 그룹, 전부 읽을 수 있게 | 의미적 정확성·주제 일치 판정은 UI만으로 보장 불가 |
| 오류 | error.code | SAFE_FAILURE / TIMEOUT / INVALID_INPUT / CONFIG_ERROR / 그 외 분리 | raw message와 원문 응답 노출 금지 |

Persona 사전: Auditor→“근거를 꼼꼼히 확인해요”; Socratic→“말의 뜻과 전제를 확인해요”; Falsifier→“반례와 예외를 찾아요”; Pragmatist→“비용과 현실성을 따져요”; Principlist→“원칙과 일관성을 따져요”; Synthesist→“서로 받아들일 범위를 찾아요”. ‘언제나 이렇게 행동한다’는 보장으로 쓰지 않는다.

정확한 발언 관계는 제품 핵심 요구지만 현재 공개 데이터로 충족할 수 없다. **이번 프런트엔드는 발언을 시간순 카드로 읽는 경험까지 완성**한다. 직전 발언은 바로 위 카드와 중복되므로 인용하지 않는다. 정확한 Callback·양보·수정 배지는 아래에 완성형 디자인을 정의하되, 서버에서 공개 표시 데이터를 제공하기 전에는 렌더링하지 않는다. 백엔드 구조 재편·추가 AI 호출·브라우저의 엔진 토큰 해독은 제안하지 않는다.

### 8.1 요청·오류 상태 규칙

요청별 단일 pending guard. `operationId`와 직전 성공 session snapshot을 기록한다. 같은 화면의 모든 진행·수정·질문·생략 버튼을 함께 잠근다. 내비게이션으로 안내 페이지를 읽는 것은 허용하되 pending 요청은 한 번만 진행한다. 돌아오면 상태를 복원한다.

설계 시간표: 0초 실제 작업명, 15초 “평소보다 오래 걸리고 있어요.”, 60초 “응답을 기다리고 있어요. 기다리기를 중단한 뒤 다시 시도할 수 있어요.” + 중단 버튼, 180초 브라우저 대기 종료. 기존 app.js의 180초를 유지한 클라이언트 상한이며 서버의 성공 시간 보장은 아니다. 서버 Timeout을 받으면 시간에 관계없이 즉시 timeout UI. 남은 초 카운트·완료율은 표시하지 않는다.

Abort는 브라우저 기다리기만 중단하며 서버 취소 보장은 없다. 중단 후 “이 창에서 기다리기를 중단했어요.”, 사용자가 재시도하면 새 operationId. 늦게 도착한 이전 응답은 무시. 같은 원본 session·command로 재시도하고 성공 응답만 commit한다. token을 임의로 수정·해석하지 않는다. 엔진의 중복 처리 방지 보장은 현재 확인하지 않았으므로 UI가 ‘서버에서 정확히 한 번’ 실행한다고 말하지 않는다.

Safe failure면 transcript·engine_token·phase·next_index를 이전 성공값에 둔다. API 오류 시 입력을 유지하고 한 화면에 오류 하나. summary 실패는 debate-step을 다시 호출하지 않고 neutral-summary만 재시도한다. 질문 등록 성공과 첫 답변 생성 실패는 분리: 질문을 다시 등록하지 않고 NEXT 재시도. 질문 등록 실패면 textarea를 유지한다. context 답변은 요청 중 후보 배열에만 추가하고 실패 시 기존 확정 배열로 되돌린다.

| 질문 대기 | awaiting_audience_question이면 Next 숨김, question/skip만 가능. 등록 성공 후 NEXT 첫 답변 요청 | 양측 같은 질문·중복 등록 없음 | 질문·생략 둘 다 end-to-end |
| 답변 순차 | A 답변→사용자 다른 쪽 답변 클릭→B 답변→Rebuttal | 질문 등록 응답을 A 답변으로 오인하지 않음 | audience_response_index와 화면 비교 |
| 단계 표시 | 서버 phase의 한글 매핑, completed 우선. 마지막 본문은 Final Focus로 남김 | 완료 후 현재 위치가 FINAL_FOCUS에 고정되지 않음 | 마지막 응답·요약 전후 |
| 요약 | completed 후 마지막 발언을 충분히 읽게 ‘토론 정리 보기’. 클릭 시 summary endpoint | 요약 실패 재시도는 summary만 | 요청 경로 기록 |
| 선택·종료 | local radio 값, 확정 후 view=done. 저장 API 없음. 새 주제에서 메모리 전부 초기화 | 이전 토론이 다음 토론에 섞이지 않음 | 두 세션 연속 진행 |
| focus·live | 단계 전환 제목 focus, 새 발언 짧은 도착 알림. 과거 읽을 땐 강제 스크롤 안 함 | 키보드 위치 보존 | Tab/ShiftTab/Enter/Space/화살표 |
| 일회성 | localStorage·DB 없음. 진행 중 새 주제는 확인 dialog. beforeunload는 진행 데이터 있을 때만 브라우저 표준 안내 | 복원 보장 표현 없음 | 새 주제 취소·확정, 새로고침 |

상태 전환표:

```text
topic.idle → topic.loading → context.question | motion.loading | topic.informational
context.question → context.submitting → context.question | context.review
context.review → motion.loading → motion.review
motion.review ↔ motion.editing → motion.saving → motion.review(edit_count=1)
motion.review → debate.loading → debate.ready
debate.ready → debate.loading → debate.ready | audience.offer | debate.finalReady
audience.offer → audience.editing → audience.submitting → audience.answerLoading
audience.offer → audience.skipping → debate.ready
audience.answerLoading → audience.answerReady → audience.answerLoading → debate.ready
debate.finalReady → summary.loading → summary.ready → choice.idle → done
모든 loading → 같은 화면.error | timeout | safeFailure → 해당 operation 재시도
```

마지막 전환 줄의 의미: 모든 loading 상태는 같은 화면의 오류로 이동하며, 해당 요청만 재시도한다. 오류 종류에 따라 입력·토론 보존 규칙은 8.1절을 따른다.

현재 API에서 질문 생략 성공은 발언 없는 CROSSFIRE 응답일 수 있다. 생략 성공 시 추가 NEXT를 한 번 호출해 Rebuttal을 시작한다. 질문 등록 성공 역시 발언 없는 응답이므로 transcript 추가 조건은 `utterance` 존재 여부. 다음 화자는 서비스의 고정 스케줄과 검증된 session으로 확실할 때만 이름을 표시하고, 그렇지 않으면 “다음 발언”이라고 쓴다.

테스트 작성은 사용자의 TDD 원칙에 따라 **실제 구현 전 실패를 확인하고 구현 후 통과**시킨다. 본 산출물은 설계 문서·정적 시안이며 운영 구현이나 운영 테스트 완료를 주장하지 않는다. 실제 API 오류·안전 실패 검수는 로컬의 명시적 테스트 환경에서 해야 하며 프로덕션 실패를 유발하지 않는다. 가짜 발언 생성기를 제품에 추가해 통과시키지 않는다.

## 11. 구현 순서와 완료 조건

1. **사용자 흐름과 정보 구조** — 세 라우트, 준비/관전/정리 상태 전환표 구현. context·정보 질문·수정·질문 생략 분기까지 경로가 끊기지 않으면 완료.
2. **모바일 핵심 레이아웃** — 390px Home/상황/Motion 입력을 16px 이상 글자와 48px 이상 터치영역으로 구현. 길이 제한·오류가 입력 옆에서 읽히면 완료.
3. **Debate 관전 화면** — 첫 발언 자동 요청, 다음 발언 수동, A/B 문자·형태·위치, 원문 이전 발언 링크. 사용자 스크롤을 빼앗지 않고 현재 위치를 찾을 수 있으면 완료.
4. **로딩·오류·안전 실패** — 모든 비동기 요청 pending 잠금·operationId·재시도·원문 보존. 실패 후 원래 단계로 복구되고 중복 발언이 없으면 완료.
5. **Neutral Summary와 사용자 선택** — 다섯 요약 그룹, 동등 A/B, 무선택 radio→명시적 확정→종료. 원문 복귀와 새 주제 초기화까지 되면 완료.
6. **데스크톱 확장** — 768px 비교 카드, 1440px rail+로그, 본문 최대640px 카드. 확대 시 한 열로 자연 전환되면 완료.
7. **디자인 시스템 정리** — 토큰·버튼·입력·카드 공통화, 미사용 기존 CSS 제거. 같은 상태에 다른 색/간격이 남지 않으면 완료.
8. **접근성** — 키보드 전체 경로, 오류 연결, 포커스, live 최소 안내, AA 대비, 200% 글자·400% 확대·고대비 검사. 실제 보조기기 확인 항목을 기록하면 완료.
9. **마이크로 인터랙션** — 8절의 의미 있는 전환만 적용. reduced-motion에서 흐름과 정보가 동일하면 완료.
10. **최종 시각 검수** — 390/768/1440 각 Home·Motion·Debate·질문·요약·선택·오류 캡처. 긴 한글·긴 입장명·최대 입력·키보드 열린 상태에서도 CTA와 본문이 겹치지 않으면 완료.

접근성은 8단계에 처음 추가하는 것이 아니라 1단계부터 반영하고 8단계에서 전수 검수한다. API 데이터 정확성 문제는 UI 완성으로 숨기지 않는다. 출석 주제의 요약 불일치는 콘텐츠 검수 항목으로 별도 해소해야 한다.

## 산출물 사용법

`UX_UI_PREVIEW.html`을 브라우저에서 연다. 화면 목록을 따라 Home, 문장 확인, 관전, 질문, 정리, 종료, 상황 질문, 실패 상태를 살펴본다. 생성 버튼을 눌러 가짜 성공을 보여주는 인터랙티브 데모가 아니라, 개발자가 그대로 옮길 수 있는 HTML/CSS 화면 자료다. 실제 앱 연결 시 10절 상태·API 계약을 구현한다. 시안의 샘플 문구와 사용자 입력값을 운영 코드의 고정 데이터로 넣지 않는다.

## 검증 기록 — 설계값과 구분되는 실측

2026-09-25 로컬 HTML을 브라우저에서 실제 열어 검사했다. 시안의 12개 화면 × 3개 폭, 총 36개 조합에서 `documentElement.scrollWidth <= documentElement.clientWidth`를 확인했다. 테스트 높이는 이 순회에서 900px. 별도로 모바일 390×844와 태블릿 768×1024 캡처도 확인했다. 활성 h1이 없던 선택 화면을 발견해 수정했고, 선택 화면은 세 폭에서 h1 1개와 가로 넘침 없음을 다시 확인했다. 서비스 기능 테스트 통과를 뜻하지 않는다.
